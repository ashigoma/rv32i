# 自由変数の静的名前解決
まず束縛変数をすべてstack frameに置くというのは前提にする
ここでlambda closure作成時・関数適用時の自由変数の名前解決をどうするかを考える
高階関数を外側からf,gとする。
- そもそもlambda closureはなぜ必要なのか
    - fが内側関数gの実体を返すとき、返したgの実体がfのfun文いくつ分外側で適用されるかは静的に決定できない。(条件分岐によってダミーを外側に渡したりgの実体を外側に渡したりできるため)
    - gの内部に自由変数xがある場合、xが束縛されたスタックフレームのいくつ後のスタックフレームで適用されているか静的にわからないので直接参照することができない
    - そのため何回関数を適用しようが変わらないgの実体自身にxのポインタまたは値を埋め込むのが一番まともな解決になる
- ではポインタを埋め込むのではなぜだめなのか
    - fの適用後fのスタックフレームはなくなるので、fで束縛された変数xがgの自由変数になっているとgの適用時にダングリングポインタになるから
- 自由変数の値はどのlambda closureに置くのか
    - 高階関数を外側からf,g,hとする。h→g→fの順に実体化される。
    - xがhの自由変数であるとする
    - 選択肢はf,g,hどのlambda closureに置くかで3通りある
        - gのclosureに置くのはよくわからない
        - fのclosureに置くと、hの適用時にfのclosureを参照する仕組みが必要。closureをつくったとき、一つ外側のclosureのポインタを埋め込むようにしておけばたどっていける。
        - hのclosureに置くと、hの実体化時にfのスタックフレームを参照する仕組みが必要。だが結局スタックフレームいくつ分というたどり方はできないのでclosureいくつ分というたどり方をする必要があり、上記のclosureのポインタを埋め込む方法が必要。
    - パフォーマンス的にはhが有効で、fとhで実装難易度に差がないからhを採用する

# 構造体とメモリ管理
- heapには文字列, lambda closureの実体が置かれる
- stackには1wordより大きなオブジェクトを置かない
- スタックフレームの構造
    - callerに対応するsp
    - calleeに対応するlambda closureのポインタ
    - 束縛変数(引数はこれの0番目とみなす) N個
- lambda closureの構造
    - 親のlambda closureのポインタ
    - 実体化が行われたときのsp
    - 関数のスタックフレームのサイズ
    - 関数の開始アドレス
    - キャプチャした自由変数たちの値

# 関数とアセンブリ
- 引数はすべてスタック渡し
- heapにはlambda closureと文字列を置く。GCはたぶん実装しない
- 関数の実体化
    - 必要な自由変数を新しいlambda closureに詰める
        - 自由変数はlambda closureをたどったあとスタックフレーム上から値コピー
- 関数の呼び出し
    - callerがスタックフレームを作る。スタックフレームの破棄もcallerが行う
    - 自由変数は渡された環境を参照すればいい
