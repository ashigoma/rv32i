# 構造体とメモリ管理
- heapには文字列, lambda closureの実体が置かれる
- stackには1wordより大きなオブジェクトを置かない
- スタックフレームの構造
    - callerのスタックフレームの先頭アドレス
    - calleeに対応する lambda closureのポインタ
    - 束縛変数(引数はこれの0番目とみなす) N個
- lambda closureの構造
    - 関数の開始アドレス
    - 関数のスタックフレームのサイズ
    - キャプチャした自由変数たちの値

# 関数とアセンブリ
- 引数はすべてスタック渡し
- heapにはlambda closureと文字列を置く。GCはたぶん実装しない
- 関数の実体化
    - 必要な自由変数、を新しいlambda closureに詰める
- 関数の呼び出し
    - callerがスタックフレームを作る。スタックフレームの破棄もcallerが行う

# 自由変数の静的名前解決
関数の外で定義された後関数内で使われるような変数が自由変数、そうでない変数は束縛変数。
自由変数の中身は
- キャプチャのために取得したいとき
    - もっとも近いスコープ上の束縛変数を値コピーする
    - スタックフレームの先頭のポインタを辿っていけばよい
- 関数内で取得したいとき
    - スタックフレームに入っているlambda closureから取得する
これを成立させるため、スタックフレーム上のpointerを値として扱わず、変数への再代入を許可しない。
コンパイル時に、関数の実体化が行われるすべての箇所において(n, f):
    - ポインタをn回たどると関数fのスタックフレームにたどり着き、束縛変数がある
    - を記録しておく

ex) 自由変数のキャプチャ時に昔のスコープのclosure内と束縛変数どちらも参照できうる例
- 関数 main, f, g, h
- xはmainの束縛変数で、f,hの自由変数
- fの中でg, gの中でhを実体化する
- gの中でhを実体化するときxの値をとってこなければいけないが、fのlambda closure内ではなくmainから直接取ってくる
